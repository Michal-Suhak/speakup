## 1. Goal and assumptions

A simple AI tutor for practising **speaking English**. You talk to the tutor by voice like to a teacher: you pick your profile, speak into the microphone, and the tutor answers by voice, keeps the conversation going about things you are interested in, and corrects important mistakes.

Assumptions for the first version:
- **private prototype** for two people (me and my cousin), run **locally**, each on their own machine, with their own `.env` file,
- each person has a **profile** (level, interests, goals, topics to avoid, correction style) that the tutor takes into account and that can be edited in the app,
- no login, no internet deployment, no database,
- all models through the **OpenAI API** (no strong GPU for local models),
- main machine: **MacBook Air (Apple Silicon)**, Chrome and Safari browsers,
- cost of a few USD per month (see section 10).

## 2. Key design decisions

| Decision | Choice | Why |
|---|---|---|
| Architecture | Classic STT → chat → TTS loop, no Realtime API | Full transcript, control over corrections, lower cost. A 2–4 s delay doesn't hurt when learning. |
| Build order | Text first, then STT, then TTS | Each layer can be tested on its own, bugs are easier to find. |
| Recording | Push-to-talk (holding a button or space) | Simpler and more reliable than automatic silence detection. |
| Corrections | **Spoken** in English, woven naturally into the reply, and **shown on screen** with a short explanation in Polish | The tutor's voice stays in one language (TTS doesn't mix Polish and English), and the Polish explanations are at hand to read. |
| Model response format | Structured JSON: `reply` + `corrections` | Text for TTS and corrections for the UI are separated, no parsing of free text. |
| Topic and level | From the **learner profile**, not a fixed list | The tutor suggests topics based on what the person likes. Each person (me, my cousin) manages their own profile. |
| Profile storage | JSON files in `profiles/` | Enough for two people, easy to inspect and fix by hand, no database. |
| Session state | In server memory | A database only when progress history is needed. |
| Dependencies | uv with `pyproject.toml` and `uv.lock` | One fast tool for Python version, virtualenv and locked dependencies; the same environment on both machines. |
| Models | Names in config, not in code | OpenAI models and prices change often. |
| Default models | Chat `gpt-6-luna`, STT `gpt-4o-mini-transcribe`, TTS `gpt-4o-mini-tts` with voice `marin` (all overridable in `.env`) | Cheapest current chat model; transcription and TTS models recommended in the OpenAI docs; `marin` is a recommended voice for quality. Re-check in stages 1–3. |
| Key check | `uv run python config.py` calls `models.list()` | One request that costs no tokens and fails clearly on a missing or wrong key. |
| New profile defaults | Pydantic defaults in the `Profile` model (`level` from config, default `interests`, `gentle`), applied when a field is omitted | One source of truth for defaults; the frontend sends only what the learner filled in. |
| Broken profile file | `GET /api/profiles` skips it and logs the file name and error type; `GET /api/profiles/{id}` returns 400 with a readable message ("… Fix or delete the file."); 500 is reserved for unexpected errors. A file counts as broken when it is unreadable, not UTF-8, invalid JSON, fails validation, or its `id` differs from the file name. Saves are atomic (temp file + rename). | Profiles are edited by hand; one bad file must not lock both learners out or leak profile content into logs. |
| Invalid `DEFAULT_LEVEL` | The app refuses to start with a clear message | Pydantic does not validate defaults, so a wrong level would be saved and then fail to load. |
| Code structure | `app.py` only wires the app; endpoints in `api/<area>.py` routers; logic in `tutor/` | Keeps `app.py` small as endpoints grow; routers stay thin and domain code stays testable without HTTP. |
| Chat call | OpenAI Responses API `responses.parse` with the `TutorTurn` Pydantic model; `corrections` comes before `reply` in the schema | Structured output without parsing free text; generating corrections first makes the model weave them into the reply. |
| Session greeting | `/api/session` sends a fixed start instruction that is not stored in the history; only the tutor's greeting is stored | The history contains only real learner and tutor messages. |
| Conversation history | Last 40 messages are sent with every turn | Enough for a 30-minute session; summarising older turns can come later if context is lost. |
| Parallel turns | One non-blocking lock per session; a second request while the tutor is answering gets 409 | Two clicks never send two requests or mix up the history. |
| Conversation errors | Unknown session 404, busy session 409, OpenAI failure or invalid answer 502, missing API key 503, all as readable JSON | The frontend can show what happened instead of a generic error. |
| Request limits | 30 s timeout, 1 retry, at most 2000 output tokens per chat call | A stalled request must not hold the session lock for minutes, and a runaway answer has a hard cap. |
| Correction check | Corrections whose `you_said` does not appear in the learner's message are dropped | The learner never sees a correction for words they did not say. |
| Answer schema | `TutorTurn` = `analysis` → `corrections` (max 5, each with `mistake_type` and `severity`; at most 3 shown, important first) → `reply`; detailed field descriptions; rules in [docs/structured-output.md](../structured-output.md) | Schema-guided reasoning: the model analyses before it corrects and replies, and every field carries its own instructions. |
| Correction style | The model lists every mistake with a severity; Python shows only `important` ones for `gentle` profiles and all for `strict` | The LLM labels, code decides: the style is applied the same way every time. |
| Session registration | A session is stored only after the greeting succeeds; sessions stay in memory until the server stops (removal comes with the end endpoint in stage 4) | Failed starts leave nothing behind. |
| Tests | pytest with FastAPI `TestClient` (`uv run pytest`), dev dependencies `pytest` and `httpx` | Readable tests with fixtures and parametrisation; endpoints are tested over HTTP, so status codes match what the frontend gets. |
| Env file template | `env.example` (no leading dot); every file starting with `.env` is gitignored and blocked for Claude | A dotless template lets one rule cover every real env file (`.env`, `.env.local`, `.env.backup`…) without exceptions. |
| New profile in the UI | The start screen asks only for a name; the id is generated from it in the browser (lowercase ASCII, Polish letters mapped, `-2`, `-3`… when taken), the backend fills the defaults, then the edit form opens | One source of defaults (the `Profile` model), no duplicated list in JavaScript. |
| Static files | `static/` is mounted at `/` after the API routers, so `/api/...` always wins | The page and the API run from one `uvicorn` process with no extra route code. |
| Voice upload | `/api/turn` takes multipart form data (dependency `python-multipart`); the backend names the file `turn.<ext>` from an allowed extension (webm, mp4, m4a, ogg, wav, mp3), otherwise 415 | The transcription API detects the format from the extension; the client's file name is never passed on. |
| Transcription | `transcriptions.create` with `STT_MODEL` and a prompt from `prompts/transcribe.md` that asks to keep the learner's mistakes and Polish words; no fixed `language` | Corrections are only as good as the transcript: STT must not "fix" grammar. Polish words stay recognisable. |
| Recording limits | Browser: under 0.5 s is not sent, recording stops at 60 s. Backend: under 1000 bytes or an empty transcript → 400 ("Nie usłyszałem…"), over 25 MB or a transcript over 1000 characters → 413 | No API call for accidental taps; a transcript fits the same limit as a typed message. |
| Voice turn lock | The session lock is reentrant and held through transcription and the reply | A second request while one is being transcribed gets 409 before paying for another transcription. |
| Microphone | Asked on the first press and kept for the session, released on "nowa rozmowa"; denied or missing mic shows a message and the text field still works | No delay on later presses, and the mic indicator turns off when the conversation ends. |
| Tutor's voice | `audio.speech.create` with `TTS_MODEL`, `TTS_VOICE` and instructions from `prompts/speak.md` (warm tone, slower for A1–B1, level from the profile); mp3 as base64 in `audio` | One voice from config, pace adapted to the level without a per-session setting. |
| TTS failure | The reply is returned with `audio: null` (logged with the error type only) instead of an error | The reply is already in the history: an error would make the learner repeat a turn the tutor has answered. |
| Session summary | `POST /api/session/{id}/end` sends the whole history with `prompts/summary.md` and the `Summary` schema (at most 3 items per list, strengths and tip in Polish); corrections that do not quote one of the learner's messages are dropped; a session where the learner never answered returns `summary: null` without a model call; the session is removed only after a successful summary, under the session lock | No cost for empty sessions, no invented mistakes, and a failed summary can be retried. |
| Usage and cost | Each session counts chat input/output tokens and STT input/output tokens from the API's `usage`, and TTS characters of the replies that were spoken; the cost uses USD rates in `config.py` (chat and STT per 1M tokens, TTS per 1M characters estimated from the per-minute price); cached input is priced as normal input | Exact counts where the API reports them; TTS reports no usage, so characters are the closest measure. The estimate errs slightly high. |
| Step logs | `tutor` and `api` log at INFO: `STT/LLM/TTS took N s (model)` per call and `Session <id> ended: <cost> USD, <counts>` | Latency per step is visible in the console without exposing learner data. |
| Playback | One `Audio` element plays every reply; "powtórz" replays it without an API call; the mic is disabled while the tutor speaks; if the browser blocks playback, a message points to "powtórz" | Nothing is recorded over the tutor's voice, and a blocked autoplay never loses the reply. |

## 3. Architecture

```
[Browser: microphone, push-to-talk]
        │  audio recording (webm in Chrome, mp4 in Safari)
        ▼
[FastAPI backend]
        ├─► OpenAI Speech-to-Text ─────► learner text
        ├─► OpenAI Chat (tutor prompt + session history)
        │        └─► JSON {reply, corrections}
        └─► OpenAI Text-to-Speech(reply) ─► mp3 audio
        │
        ▼
[Browser] plays the voice, shows the transcript and corrections
```

### Stack
- **Backend:** Python 3.11+, FastAPI, uvicorn, official `openai` SDK, `python-dotenv`
- **Dependencies:** uv (`pyproject.toml` + committed `uv.lock`); run everything with `uv run`
- **Frontend:** plain HTML + CSS + JavaScript (no framework, no build step), `MediaRecorder` for recording
- **API key:** only in `.env` on the backend. Never in the frontend or the repository.
- **Models:** before implementation check the current OpenAI docs for recommended models and prices:
  - transcription (e.g. `gpt-4o-mini-transcribe` / `gpt-4o-transcribe` / `whisper-1`),
  - chat: an economical, fast model with structured outputs (JSON schema) support,
  - TTS (e.g. `gpt-4o-mini-tts` or newer), with voice selection.

## 4. Tutor behaviour

### Learner profile (`profiles/<id>.json`)
One JSON file per person, created and edited in the app. Personal data, so `profiles/` is gitignored.
```json
{
  "id": "michal",
  "name": "Michał",
  "level": "B1",
  "interests": ["travel", "technology", "football"],
  "goals": "Speak more fluently in meetings at work",
  "avoid_topics": ["politics"],
  "correction_style": "gentle"
}
```
- `id`: generated from the name on creation, must match `^[a-z0-9-]{1,32}$`. The backend rejects any other id with 400 before touching the file system, so an id can never point outside `profiles/`.
- `level`: CEFR A1–C2, default `B1`.
- `interests`: topics the tutor proposes on the start screen. A new profile is pre-filled with the default list: Travel, Work, Hobbies, Food, Movies & Books, Daily routine, Technology, Job interview.
- `correction_style`: `gentle` (only mistakes that block understanding or repeat often) or `strict` (every grammar and word-choice mistake).
- Free-text fields are validated in the Pydantic profile model: `name` ≤ 40 characters, `goals` ≤ 300, `interests` and `avoid_topics` at most 20 items of ≤ 40 characters each. The custom topic from the start screen is limited to 80 characters.

### System prompt (`prompts/tutor.md`)
A file with placeholders filled from the session and the profile: `$topic`, `$level`, `$name`, `$interests`, `$goals`, `$avoid_topics`, `$correction_style`.
- Rendered with `string.Template.substitute` (not `str.format`), so literal braces in the prompt, such as the JSON output example, are safe, and a missing placeholder raises an error instead of being sent to the model.
- Lists are joined with ", "; an empty list or empty text renders as "none".
- Learner-provided values (topic and profile fields) are placed inside a `<learner_profile>` section that the prompt declares as data about the learner, never as instructions.

Guidelines:
- Speaks **English**, adapts vocabulary and sentence length to the profile level (A1–C2).
- **Short:** 2–4 sentences per reply. The learner should talk more than the tutor.
- **One question at a time**, always ends with a question or an encouragement.
- Stays on topic but allows natural digressions.
- Corrects mistakes according to `correction_style`: with `gentle` only **important** ones (grammar that changes meaning, frequent mistakes, wrong word) and lets small slips pass, so fluency isn't broken; with `strict` every grammar and word-choice mistake.
- Never brings up `avoid_topics`; may refer to `interests` and `goals` to keep the conversation personal.
- In `reply` the correction is woven in naturally (e.g. "Oh, you *went* there yesterday? Nice!"), without lectures.
- Ignores obvious speech recognition errors that are not the learner's mistakes.
- When the learner doesn't know how to say something, or drops in a Polish word, suggests the English equivalent.
- `reply` must be TTS-friendly: no markdown, emoji, lists or brackets.
- First message of the session: a short greeting and the first question on the chosen topic.

### Model response format (structured output)
```json
{
  "reply": "English text that will be read aloud.",
  "corrections": [
    {
      "you_said": "I go there yesterday",
      "better": "I went there yesterday",
      "explanation_pl": "Czas przeszły: go → went."
    }
  ]
}
```
`corrections` may be an empty list. Not every turn needs a correction.

### Session summary (`prompts/summary.md`)
After clicking "Zakończ sesję" (End session) the model gets the whole history and returns JSON:
```json
{
  "top_corrections": [{"you_said": "...", "better": "...", "explanation_pl": "..."}],
  "useful_vocabulary": [{"word": "...", "meaning_pl": "...", "example": "..."}],
  "strengths": ["..."],
  "tip_pl": "Jedna konkretna wskazówka na następny raz."
}
```
At most 3 most important corrections and 3 useful words. Explanations in Polish, examples in English.

├── profiles/              # one JSON per learner, gitignored

### Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/` | app page |
| `GET` | `/api/profiles` | → list of `{id, name, level}` |
| `GET` | `/api/profiles/{id}` | → full profile |
| `PUT` | `/api/profiles/{id}` | full profile → saved profile (creates the file if it doesn't exist) |
| `POST` | `/api/session` | `{profile_id, topic}` → `{session_id, reply, audio?}`: the tutor greets and asks the first question; level and preferences come from the profile |
| `POST` | `/api/text` | `{session_id, text}` → `{reply, corrections, audio?}`: text turn (for testing and as a fallback mode) |
| `POST` | `/api/turn` | multipart: `session_id` + audio file → `{user_text, reply, corrections, audio?}` |
| `POST` | `/api/session/{id}/end` | → `{summary, duration_seconds, usage, cost_usd}` (`summary` is `null` when the learner never answered) |

- Audio as base64 mp3 in JSON (simpler for the MVP). `audio` is `null` when speech synthesis fails; the frontend then shows the text only.
- Each session has a **lock**: a parallel turn for the same session returns 409, so several requests are never sent at once.
- OpenAI errors (network, rate limit, bad key) are returned as a readable JSON message, without crashing the server.

## 6. Interface

1. **Start:**
   - pick your profile or create a new one; "Edytuj profil" (Edit profile) opens a form with all profile fields,
   - pick a topic: one of your `interests` shown as buttons, or type a custom topic,
   - "Start" button. The level is taken from the profile, there is no separate level picker.
2. **Conversation:**
   - large microphone button + **holding space** = recording,
   - clear state: *ready / recording / processing / tutor speaking*; the button is disabled while processing,
   - chat-like transcript; under each learner message expandable corrections (`you_said → better` + explanation in Polish),
   - "Powtórz" (Repeat) button to replay the last reply,
   - text field as a fallback alternative to the microphone,
   - "Zakończ sesję" (End session) button.
3. **Summary:** 3 corrections, 3 words, strengths, a tip, session duration and approximate cost.

Simple, readable look. The page runs at `http://localhost`, where browsers allow microphone access.

## 8. MVP completion criteria
- [ ] I create and edit my profile in the app, and the changes are saved in `profiles/<id>.json`.
- [ ] I pick my profile and a topic from my interests (or a custom one), and the tutor starts the conversation by voice at my profile's level.
- [ ] I record an utterance and the transcript appears in the app.
- [ ] The tutor answers briefly, following the instructions, keeping the session context.
- [ ] Important mistakes are corrected and visible with an explanation in Polish.
- [ ] The reply is played by voice and can be replayed.
- [ ] API and microphone errors are handled without freezing the app.
- [ ] A 30-minute session works without restart.
- [ ] After the session there is a summary and the measured cost.
- [ ] My cousin runs the project on their own using the README.

## 10. Rough budget

Assumption: 2 people × 30 min per week ≈ 4 h of conversation per month (the learner speaks about half the time). With economical models the cost is **a few USD per month**, and TTS is usually the largest part. Estimate from the ChatGPT plan: about 1.6–4 USD per month (STT ~0.5, text model ~0.1–0.5, TTS ~1–3). These are rough numbers only. The real cost will be measured by the counter from stage 4, and current rates must be checked in the OpenAI pricing. The API is billed separately from the ChatGPT subscription. It's worth setting a spending limit on the API account.

## 11. Implementation rules
- Work in stages in the order of section 7. After each stage stop and show how to test it.
- Simple, readable code without unnecessary abstractions. Code, comments and README in English.
- OpenAI calls only in the backend.
- Prompts in `prompts/` files, not in code.
- Model names, voice and rates in config.
- Before implementation check the current OpenAI API (structured outputs, transcription, TTS) instead of relying on memory.
